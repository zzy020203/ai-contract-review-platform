# 第一部分 需求分析

## 1. 项目背景

### 1.1 行业痛点
企业合同审查是法务部门的高频核心工作，但长期面临以下问题：

| 痛点 | 具体表现 | 影响 |
|---|---|---|
| **效率低下** | 一份 50 页合同人工审查需 2-4 小时，年度合同量激增时法务人员不堪重负 | 审查周期长，影响业务推进速度 |
| **标准不一** | 不同法务人员审查风格各异，风险识别口径不一致，遗漏关键条款时有发生 | 合同质量参差不齐，隐性风险累积 |
| **知识断层** | 新人缺乏经验积累，历史审查经验无法系统化沉淀 | 重复劳动、同质化问题反复出现 |
| **合规压力** | 法律法规更新频繁（如《民法典》修订、行业监管新规），人工追踪不及时 | 合规风险敞口持续扩大 |
| **审计困难** | 审查过程无记录、无追溯，出现争议时无法还原审查决策链路 | 无法定责、无法改进 |

### 1.2 项目目标
基于 DocuMind 现有技术底座（FastAPI + Vue 3 + 完整 RBAC），通过二次开发构建一套 **AI 驱动的企业智能合同审查平台**，实现：

- **效率提升**：AI 自动完成初筛，审查周期从小时级压缩到分钟级
- **标准统一**：规则库 + 大模型双重校验，风险识别口径一致可追溯
- **知识沉淀**：审查经验自动入库，越用越聪明
- **人机协同**：高风险条款强制人工复核，低风险建议一键采纳
- **全链路可审计**：从上传到出报告的每一步操作留痕

### 1.3 产品定位
> **定位**：企业法务部门的 AI 审查助手  
> **阶段**：AI 辅助为主，人做最终决策；逐步向 AI 自主审查 + 人工抽检演进  
> **边界**：不做合同全生命周期管理（起草→谈判→签署→归档），聚焦 **审查** 环节

## 2. 目标用户与角色

### 2.1 角色定义

| 角色 | 权限码 | 典型用户 | 核心诉求 |
|---|---|---|---|
| 系统管理员 | `admin` | IT/运维 | 系统配置、账号管理、监控运维 |
| 法务主管 | `legal_lead` | 法务部门负责人 | 全局审查质量管控、复核高风险、看板决策 |
| 法务专员 | `legal_staff` | 一线法务 | 日常合同上传、AI 审查复核、规则库维护 |
| 业务部门 | `requester` | 销售/采购/HR | 发起审查、查看审查结果、下载报告 |

### 2.2 典型用户旅程

```
[法务专员上传合同] → [AI 自动解析提取条款] → [并行：风险识别 + 合规检查]
→ [低风险：AI 建议直接采纳 → 生成报告]
→ [高风险：进入复核队列 → 主管人工决策 → 采纳/修改/驳回 → 生成报告]
→ [报告归档 + 审计留痕]
```

## 3. 功能需求

### 3.1 功能模块总览

```
企业智能合同审查平台
├── 合同管理模块（上传 / 列表 / 详情 / 下载）
├── AI 审查引擎（解析 / 条款提取 / 风险识别 / 合规检查 / 建议生成）
├── 规则库（CRUD / 启停 / 版本管理 / 向量化）
├── 知识库（历史案例 / 模板合同 / 法律法规 / 向量检索）
├── 人机协同复核（复核队列 / 详情比对 / 采纳反馈）
├── 报告中心（审查报告 Word 导出 / 风险分布统计）
├── 审计日志（全操作留痕 / 条件筛选 / 导出）
├── 数据看板（多维度指标 / 趋势图表 / ECharts）
├── 系统监控（组件健康探测 / Prometheus 指标 / 自动刷新）
└── 系统管理（RBAC：用户/角色/权限/菜单/部门 —— 复用 DocuMind 全部现有能力）
```

## 4. 非功能需求

### 4.1 性能要求

| 指标 | 目标 |
|---|---|
| 单合同审查时长 | ≤ 2 分钟（中等复杂度合同，10-30 页） |
| 并发审查能力 | ≥ 10 个任务并行（Celery worker 扩展） |
| API 响应时间 | 常规列表查询 ≤ 500ms，复杂查询 ≤ 2s |
| 系统可用性 | ≥ 99%（单机部署） |
| 向量检索 P99 | ≤ 200ms |

### 4.2 安全要求

| 维度 | 措施 |
|---|---|
| 鉴权 | JWT 双 Token + RBAC 三层防护（后端接口鉴权 + 数据过滤 + 前端隐藏） |
| 数据隔离 | 不同部门/角色的数据按权限过滤 |
| 文件安全 | 上传文件类型校验、大小限制、病毒扫描（可选） |
| 审计 | 所有关键操作留痕，不可篡改 |
| 传输 | 生产环境 HTTPS，内部接口 X-Internal-Token 鉴权 |
| LLM 安全 | 私有化 DeepSeek 部署 + API Key 轮转机制 |

### 4.3 可扩展性

| 方向 | 设计 |
|---|---|
| LLM 切换 | LLM 接入层统一抽象，可在 DeepSeek/通义/文心/私有化模型间切换 |
| OCR 引擎 | DocuMind 解析层可替换阿里 OCR / PaddleOCR / Tesseract |
| 向量库 | 预留 PGVector 兜底方案，Milvus 不可用时自动降级 |
| 并发扩展 | Celery worker 可横向扩容 |

### 4.4 可维护性

- 统一响应结构 `{code, message, data}`
- 统一日志格式，关键链路打点
- Swagger 自动生成接口文档（FastAPI 自带）
- 数据库迁移脚本管理（Alembic，可选引入）

## 9. AI 审查工作流设计

### 9.1 LangGraph StateGraph 节点图

```
                    ┌─────────────┐
                    │   START     │
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │  docparse   │ ← 文档解析（PDF/Word/OCR）
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │extract_clauses│ ← 条款提取（规则匹配 + LLM 分类）
                    └──────┬──────┘
                           ▼
              ┌────────────┴────────────┐
              ▼                         ▼
       ┌─────────────┐          ┌─────────────┐
       │ risk_identify│          │compliance_check│ ← 并行节点
       │ (LLM+规则库)  │          │ (LLM+知识库)    │
       └──────┬──────┘          └──────┬──────┘
              └────────────┬────────────┘
                           ▼
                    ┌─────────────┐
                    │   suggest   │ ← 合并风险 + 生成 AI 建议
                    └──────┬──────┘
                           ▼
                  ┌────────┴────────┐
                  ▼                 ▼
           ┌──────────┐      ┌──────────┐
           │ 直接出报告 │      │ human_review│ ← interrupt_before
           │(低风险)   │      │ (高风险)    │   人工确认后继续
           └────┬─────┘      └──────┬────┘
                │                    │
                └────────┬───────────┘
                         ▼
                  ┌─────────────┐
                  │   report    │ ← 生成结构化审查报告
                  └──────┬──────┘
                         ▼
                  ┌─────────────┐
                  │    END      │
                  └─────────────┘
```

### 9.2 工作流核心逻辑

| 节点 | 输入 | 处理 | 输出 | 关键技术 |
|---|---|---|---|---|
| docparse | 文件路径 | 按扩展名选择解析器 | 全文文本 | PyMuPDF / python-docx / Tesseract OCR |
| extract_clauses | 全文文本 | 先规则匹配标题，再 LLM 分类 | 条款列表（编号/标题/类型/原文） | DeepSeek + 正则规则 |
| risk_identify | 条款列表 + 规则库向量检索结果 | LLM + 规则并行扫描 | 每个条款的风险等级 + 描述 | DeepSeek + Milvus 语义检索 |
| compliance_check | 条款列表 + 知识库向量检索结果 | 对照法规 + 历史案例检查 | 合规问题清单 | DeepSeek + Milvus |
| suggest | 风险 + 合规 + 历史案例 | LLM 生成修改建议 + 理由 | 每个风险的 AI 建议 | DeepSeek |
| human_review | 高风险条款 | **interrupt_before** 暂停等待人工 | 法务决策结果（accept/modify/reject） | LangGraph interrupt |
| report | 全部决策结果 | 组装结构化报告 + 生成 Word | 报告文件路径 | python-docx |

### 9.3 中断恢复机制

```python
# LangGraph 工作流定义（伪代码）
graph = StateGraph(ReviewState)
graph.add_node("docparse", ...)
graph.add_node("extract_clauses", ...)
graph.add_node("risk_identify", ...)
graph.add_node("compliance_check", ...)
graph.add_node("suggest", ...)
graph.add_node("human_review", ...)
graph.add_node("report", ...)

# human_review 前中断，等待人工决策
graph.add_edge("suggest", "human_review")
graph.add_node("human_review", ...)
graph.add_edge("human_review", "report")

# checkpoint 用 PostgreSQL
checkpointer = PostgresSaver.from_conn_string(db_url)
app = graph.compile(checkpointer=checkpointer)

# 启动 / 恢复审查
result = await app.ainvoke(
    input_data,
    config={"configurable": {"thread_id": task.thread_id}}
)
# 下次带相同 thread_id + 人工决策结果，自动从中断点继续
```

### 9.4 Worker 与后端的协作模式

```
[上传合同] ──► [后端创建任务 + Celery delay] ──► [Celery worker 接收任务]
                                 │
                                 ├─ 调用 LangGraph 工作流
                                 │     ├─ 规则检索 → POST /api/internal/rag/search-rules
                                 │     ├─ 知识库检索 → POST /api/internal/rag/search-knowledge
                                 │     ├─ 进度回传 → POST /api/internal/task/progress
                                 │     └─ 完成回传 → POST /api/internal/task/complete
                                 │
[人工复核] ──► [后端 /api/review/{id}/decide] ──► [后端恢复 LangGraph 工作流]
                                 │
[完成] ──► [Worker 生成报告 + 审计日志]
```

> **为什么 worker 通过 HTTP 调后端？**
> 因为 Milvus Lite 是单进程独占锁文件，多进程同时打开必报 `DataDirLockedError`。worker → 后端内部接口 → 后端操作 Milvus，避免跨进程锁冲突。生产环境用 Milvus Standalone/Cluster 则无此问题。

## 13. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| DeepSeek API 网络不稳定 | 中 | AI 审查卡顿/失败 | 接入层加降级策略（规则兜底）、支持切换备用模型（通义/文心） |
| Milvus Lite 跨进程锁冲突 | 高 | worker 与后端同时操作时崩溃 | worker 统一走后端内部接口访问 Milvus（已设计）；生产换 Milvus Standalone |
| LangGraph checkpoint 数据量膨胀 | 中 | PG 表快速增大 | 定期清理历史 checkpoint；PostgresSaver 支持过期清理配置 |
| 中文合同 OCR 准确率低 | 中 | 图片合同无法正确解析 | 优先推荐 Word/PDF 上传；OCR 降级为 PaddleOCR（本地部署）或阿里 OCR |
| MySQL→PG 迁移数据丢失 | 低 | RBAC 表数据缺失 | 迁移脚本先备份再迁移；迁移后逐表校验记录数一致性 |
| 用户习惯原有系统 | 中 | 改造后体验断裂 | 登录/用户管理/角色权限保持完全不变；仅替换业务内容 |
