## 1. 引言

### 1.1 编写目的

本文档描述企业智能合同审查平台的技术实现方案，包括总体架构、核心模块设计（LangGraph 多 Agent 工作流、RAG 检索、人机协同）、数据模型、接口设计、部署方案与安全设计，作为开发落地与代码评审的技术基线。

### 1.2 技术栈总览

| 层次 | 技术选型 |

| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + ECharts，WebSocket/SSE 实时通信 |

| 部署运维 | Docker 多阶段构建 + Docker Compose + Nginx 反向代理 + Prometheus + Grafana |

## 2. 总体架构

### 2.1 架构分层

```
┌──────────────────────────────────────────────────────────┐
│ 接入层    Nginx（反向代理 / TLS 终止 / SSE·WS 代理）       │
├──────────────────────────────────────────────────────────┤
│ 前端层    Vue 3 审查工作台（上传 / 风险视图 / 修订对比 /    │
│           复核队列 / 规则管理 / 数据看板）                  │
├──────────────────────────────────────────────────────────┤
│ 服务层    FastAPI 核心服务                                │
│           ├─ 合同接入（上传/任务创建）                     │
│           ├─ 任务编排 API（启动/状态/复核/报告）           │
│           ├─ 规则与知识库 API                              │
│           └─ 认证鉴权（JWT + RBAC）/ 审计                  │
├──────────────────────────────────────────────────────────┤
│ AI 编排层 LangGraph 多 Agent 工作流                        │
│           解析→条款提取→风险识别∥合规检查→建议生成          │
│           →人工复核（interrupt）→报告生成                   │
│           ├─ RAG 检索子系统（Milvus + BGE）                │
│           └─ DeepSeek 私有化模型服务（HTTP）               │
├──────────────────────────────────────────────────────────┤
│ 数据层    PostgreSQL / Redis / Milvus / 文件存储            │
├──────────────────────────────────────────────────────────┤
│ 运维层    Docker Compose 编排 / Prometheus + Grafana       │
│           健康检查 / 日志收集                              │
└──────────────────────────────────────────────────────────┘
```

### 2.2 关键架构决策

| 决策点 | 方案 | 理由 |
| --- | --- | --- |
| 前后端形态 | 前后端分离，Nginx 统一入口 | 职责清晰，便于私有化一体交付 |
| 审查流程建模 | LangGraph StateGraph 有向图编排 | 流程含并行、条件分支、人工中断，图模型天然匹配 |
| 长任务执行 | Celery 异步执行工作流 + SSE/WS 推送进度 | 审查耗时分钟级，不能阻塞 HTTP 请求 |
| 状态持久化 | PostgresSaver checkpoint + thread_id 隔离 | 支持中断恢复、多任务隔离、人工复核续跑 |
| AI 建议落地 | append-only 版本模型 + Diff 引擎 | 修订历史不可篡改，满足留痕审计要求 |
| 模型接入 | 私有化 DeepSeek，OpenAI 兼容协议抽象 | 数据不出内网，模型可替换 |

## 3. 核心模块设计

### 3.1 LangGraph 多 Agent 工作流

#### 3.1.1 图结构设计

工作流基于 `StateGraph` 构建，节点即 Agent，共享一个全局 State：

```python
class ReviewState(TypedDict):
    task_id: str                    # 审查任务 ID（= thread_id）
    contract_id: str
    file_path: str                  # 合同原文路径
    raw_text: str                   # 解析后的全文
    clauses: list[Clause]           # 结构化条款
    risks: list[RiskItem]           # 风险识别结果
    compliance_issues: list[Issue]  # 合规检查结果
    suggestions: list[Suggestion]   # 修改建议
    review_status: str              # 状态机
    human_feedback: dict            # 人工复核处置
    report_path: str
    error: str | None
```

#### 3.1.2 节点与路由

```
parse（解析）
  → extract_clauses（条款提取）
  → ┌─ risk_identify（风险识别）─┐
    └─ compliance_check（合规检查）┘ 并行汇合
  → suggest（修改建议生成）
  → human_review?（条件边：存在高风险 → interrupt 中断；否则直达报告）
  → report（报告生成）→ END
```

| 设计点 | 实现 |
| --- | --- |
| 并行执行 | 风险识别与合规检查无依赖，由 StateGraph 并行扇出、汇合后进入下一节点，缩短端到端耗时 |
| 条件路由 | `Conditional Edges`：建议生成后判断是否存在高风险项，决定进入人工复核或直接出报告 |
| 人工中断 | 图编译时配置 `interrupt_before=["human_review"]`，高风险任务在复核节点前挂起，等待人工处置 |
| 中断恢复 | 处置完成后通过 `update_state` 写入复核结果，以同一 `thread_id` 调 `stream(None, config)` 从 checkpoint 续跑 |
| 状态持久化 | `PostgresSaver` 作为 checkpointer，每节点执行后落盘；服务重启后任务可恢复，不重复执行 |
| 多任务隔离 | 每个审查任务一个 `thread_id`，State、checkpoint、复核上下文完全隔离 |
| 容错 | 节点级 try/except + 有限重试；重试耗尽置任务失败态并告警，错误写入 `state.error` |

#### 3.1.3 各 Agent 职责

| Agent 节点 | 输入 | 职责 | 输出 |
| --- | --- | --- | --- |
| parse | 文件路径 | 提取文本、保留章节结构；扫描件/加密件报错 | raw_text |
| extract_clauses | raw_text | LLM + 规则混合切分条款、条款分类、低置信度标记 | clauses |
| risk_identify | clauses + RAG 检索 | 逐条款风险识别，输出等级/类型/依据/置信度 | risks |
| compliance_check | clauses + 规则库 | 规则引擎校验必备条款、一致性、禁用表述 | compliance_issues |
| suggest | risks + issues | 条款级修改建议（建议文本 + 理由 + 引用） | suggestions |
| human_review | 高风险项 | 挂起等待人工处置（接受/拒绝/编辑） | human_feedback |
| report | 全部结果 | 模板引擎渲染审查报告 | report_path |

### 3.2 RAG 与向量检索子系统

#### 3.2.1 知识库构成

- **规则库**：法务合规规则（条款级审查口径），支持版本管理与启停。
- **历史合同库**：历史审查案例，作为风险识别的参照样本。
- **标准模板库**：公司标准合同模板，用于条款差异比对。

#### 3.2.2 检索管线

```
文档上传 → 清洗 → 语义切片（按条款/章节边界）→ BGE Embedding 向量化
        → Milvus 集合（按库类型 + 版本建分区）
审查时：条款文本 → BGE 向量化 → Milvus Top-K 相似检索
        → 结果注入 Agent 提示词（规则依据/历史案例/模板参照）
```

| 设计点 | 实现 |
| --- | --- |
| Embedding | BGE 中文向量模型，私有化部署 |
| 向量库 | Milvus，按 `collection = 库类型` 划分，`partition = 规则版本`，规则升级不影响在途任务 |
| 检索策略 | Top-K 相似检索 + 相似度阈值过滤，低于阈值不注入，避免噪声 |
| 与 LangGraph 集成 | 检索封装为工具函数，风险识别/合规检查节点按需调用 |
| 引用溯源 | 每条风险记录命中的规则编号/模板出处，报告中可溯源 |

### 3.3 人机协同设计

#### 3.3.1 复核闭环

```
工作流 interrupt（高风险挂起）
  → 后端将任务写入复核队列 + WebSocket 通知前端
  → 法务在工作台处置（接受/拒绝/编辑 AI 建议）
  → 提交后后端 update_state 写入处置结果
  → 工作流从 checkpoint 恢复 → 报告生成
```

#### 3.3.2 版本与 Diff 模型

- **append-only 版本模型**：每次处置产生一个新版本记录，历史版本只增不改，满足审计不可篡改要求。
- **Diff 引擎**：条款级文本差异计算（原文 vs 修订稿），前端按条款高亮渲染增删改。
- **处置日志**：操作人、时间、处置动作、处置前后内容全量落库。

### 3.4 后端核心服务设计

#### 3.4.1 模块划分

| 模块 | 职责 | 关键技术 |
| --- | --- | --- |
| 认证鉴权 | 登录签发/校验 JWT，RBAC 权限码校验 | JWT + 依赖注入 `require_perm` |
| 合同接入 | 上传、格式校验、任务创建 | FastAPI UploadFile + 文件存储 |
| 任务编排 | 启动工作流、状态查询、复核提交、报告获取 | Celery 投递 + LangGraph invoke |
| 进度推送 | 工作流事件实时推送 | SSE（进度）+ WebSocket（复核通知） |
| 规则知识库 | 规则/历史合同/模板 CRUD、向量化入库 | SQLAlchemy + Milvus |
| 审计 | 关键操作审计日志 | 中间件/装饰器统一记录 |

#### 3.4.2 异步执行模型

- HTTP 接口只做参数校验与任务投递（Celery），立即返回 `task_id`。
- Worker 执行 LangGraph 工作流，节点事件经 Redis 通道广播，SSE 网关推送到前端。
- 长任务与 Web 进程解耦，保证接口低延迟、任务可横向扩容。

### 3.5 前端审查工作台设计

| 视图 | 功能要点 |
| --- | --- |
| 任务列表 | 状态筛选、进度实时刷新（SSE）、失败重发 |
| 审查详情 | 条款树 + 风险清单双栏联动，风险按等级着色，依据可溯源查看 |
| 修订对比 | Diff 引擎驱动的条款级对比视图，支持接受/拒绝/编辑 |
| 复核队列 | 高风险任务认领、批注、提交处置 |
| 数据看板 | ECharts 展示审查量、风险分布、平均耗时 |
| 规则管理 | 规则 CRUD、启停、版本查看 |

工程化：Vite 构建、TypeScript 强类型、Pinia 模块化状态、Axios 拦截器统一鉴权与错误处理、Vue Router 导航守卫按权限码控制页面访问。

## 5. 接口设计（核心 API）

统一前缀 `/api`，统一响应结构 `{code, message, data}`；除登录外全部接口走 JWT 鉴权 + RBAC 权限码校验。

| 方法 | 路径 | 说明 | 权限码 |
| --- | --- | --- | --- |
| POST | /api/auth/login | 登录签发 JWT | 公开 |
| POST | /api/contract/upload | 上传合同并创建审查任务 | contract:upload |
| POST | /api/review/{task_id}/start | 启动审查工作流（投递 Celery） | review:start |
| GET | /api/review/{task_id}/status | 查询任务状态与当前节点 | review:view |
| GET | /api/review/{task_id}/events | SSE 订阅审查进度 | review:view |
| GET | /api/review/queue | 人工复核队列（按等级/时间筛选） | review:audit |
| POST | /api/review/{task_id}/feedback | 提交复核处置（接受/拒绝/编辑），触发工作流恢复 | review:audit |
| GET | /api/review/{task_id}/report | 获取审查报告 | review:view |
| GET | /api/review/{task_id}/report/export | 导出报告（PDF/Word） | review:export |
| GET/POST/PUT/DELETE | /api/rule[/{id}] | 审查规则管理（版本化） | rule:manage |
| POST | /api/knowledge/upload | 知识库文档上传与向量化 | knowledge:manage |
| GET | /api/knowledge/search | 知识库相似检索验证 | knowledge:view |

### 复核处置请求示例

```json
POST /api/review/{task_id}/feedback
{
  "actions": [
    {"suggestion_id": 101, "action": "accept"},
    {"suggestion_id": 102, "action": "edit", "edited_text": "违约方应承担不超过合同总额 20% 的违约金"},
    {"suggestion_id": 103, "action": "reject", "comment": "该风险经确认可接受"}
  ]

```

## 6. 部署与运维设计

### 6.1 Docker Compose 编排

| 服务 | 镜像/构建 | 职责 |
| --- | --- | --- |
| nginx | nginx 官方镜像 | 反向代理、TLS 终止、静态资源、SSE/WS 代理 |
| frontend | 多阶段构建（Node 构建 → Nginx 承载） | 前端静态资源 |
| backend | 多阶段构建（Python slim） | FastAPI 服务（uvicorn 多 worker） |
| celery-worker | 同 backend 镜像 | 执行 LangGraph 工作流 |
| deepseek-server | 私有化模型推理服务 | DeepSeek 模型 API（GPU 节点） |
| milvus | milvus 官方镜像 | 向量检索 |
| postgres | postgres 官方镜像 | 业务库 + checkpoint |
| redis | redis 官方镜像 | 缓存 / 队列 / 事件通道 |
| prometheus / grafana | 官方镜像 | 监控与可视化 |

### 6.2 运维要点

- **一键部署**：`docker compose up -d` 完成全栈拉起，配套初始化脚本（建库、建集合、预置角色）。
- **健康检查**：backend `/healthz`、milvus/postgres/redis 容器 healthcheck，Nginx 层探测。
- **监控告警**：Prometheus 采集接口耗时、任务队列长度、工作流失败率；Grafana 看板 + 告警规则。
- **日志**：结构化日志（JSON）输出到 stdout，Docker 日志驱动收集，任务级 trace_id 贯穿工作流。

## 7. 安全设计

| 层面 | 措施 |
| --- | --- |
| 认证 | JWT 签发与校验，Token 过期机制，登出作废 |
| 授权 | RBAC 权限码控制到接口级与页面级，敏感操作（复核/导出/规则变更）独立权限 |
| 数据安全 | 全组件私有化部署，支持离线运行；合同数据不出内网；存储访问最小权限 |
| 传输安全 | Nginx 终止 TLS，内网服务间明文（隔离网络内） |
| 审计 | 关键操作全量审计日志，修订版本 append-only 不可篡改 |
| AI 安全 | AI 建议必须人工确认后生效；检索注入带来源标注；低置信度结果强制人工处理 |

## 8. 性能与可靠性设计

| 目标 | 手段 |
| --- | --- |
| 审查提速 | 风险识别与合规检查并行执行；条款级并发调用模型；Top-K 检索结果缓存 |
| 接口低延迟 | 长任务 Celery 异步化，接口只做投递与查询 |
| 断点恢复 | PostgresSaver checkpoint + thread_id 恢复，节点幂等设计避免重复副作用 |
| 任务隔离 | thread_id 维度隔离 State / checkpoint / 复核上下文 |
| 失败兜底 | 节点重试 → 失败态 + 告警；复核超时提醒；失败任务支持重发 |
| 可观测 | 节点级耗时埋点、模型调用量统计、Prometheus 指标 + Grafana 看板 |

## 9. 扩展性设计

1. **新增审查维度**：新增 LangGraph 节点接入图即可（如税务条款专项 Agent），主流程不变。
2. **模型替换**：模型调用层抽象为 OpenAI 兼容协议，可平滑切换其他私有化模型。
3. **规则热更新**：规则按版本管理、向量按版本建 partition，新版本只对后续任务生效。
4. **横向扩容**：celery-worker 无状态可水平扩展；Milvus/PostgreSQL 可独立升级为集群。
5. **后续演进**：预留 OCR 接入位、电子签章对接位与领域微调管线（基于审查历史构造 SFT 数据）。
